## ARM sizes and RAM comparison

Compiler: `arm-none-eabi-gcc 9.2.1 20191025`
(`15:9-2019-q4-0ubuntu1`), WSL Ubuntu.

Same baseline and revised build command, from `build_make/`:

```sh
make S2_ONLY=1 CONSOLE=uart WIFI=none TEST=1 S2_ENCODER_ENABLED=1 -j8
arm-none-eabi-size mtk3pico_smp1_uart_s2_enc_test.elf
```

SMP=1 and command timeout=1000 ms are defaults. Both builds compiled and
linked successfully. Actual ARM symbols/types were inspected; this toolchain
uses short enums, so a host assumption of 20-byte status would be incorrect.

| Target measurement | Before | After | Difference |
|---|---:|---:|---:|
| Published motion status object | 16 B | 12 B | -4 B |
| Motor-task working status object | 16 B | 12 B | -4 B object; stack reservation unchanged |
| Movement message including kernel header/alignment | 16 B | 12 B | -4 B / message |
| Eight-message pool data | 128 B | 96 B | -32 B requested at runtime |
| Native encoder API view | 60 B | 64 B | +4 B transient capture timestamp |
| ELF `text` | 53,143 B | 54,439 B | +1,296 B |
| ELF `data` | 12 B | 12 B | 0 |
| ELF `bss` | 16,088 B | 16,084 B | -4 B |
| Linked static RAM (`data+bss`) | 16,100 B | 16,096 B | -4 B |
| Flash load (`text+data`) | 53,155 B | 54,451 B | +1,296 B |

The kernel's fixed-pool blocks round to four bytes; its allocator rounds to
eight bytes. Both 128 and 96 bytes are already aligned. The runtime pool
therefore leaves 32 more bytes available in the existing kernel heap, with
the same allocation metadata. This is **separate from** the four-byte static
RAM reduction; the heap and the 2048-byte motor task stack are not resized.
Do not add a four-byte working-object reduction to the linked RAM reduction.
Stack high-water usage has not been measured.

The linker discards unreferenced functions. These figures describe this
standalone test profile; connecting the telemetry adapters in Buddy 1 can
retain more codec code. A full-system RAM total cannot be measured from this
branch's currently incomplete full-application build.

## Message sizes

| Record | Native baseline/reference | New application payload | With common envelope |
|---|---:|---:|---:|
| Movement mailbox block (ARM) | 16 B | 12 B including RTOS metadata | Not sent over MQTT |
| Motion status | 16 B native API object | 7 B | 9 B |
| Encoder status | 60 B original native API object | 13 B | 15 B |

The external records deliberately omit RTOS pointers, duplicate diagnostic
counts and the exact kernel error; they preserve the documented control and
routine telemetry fields. Native API objects were never a portable network
format. There is no established old S2 MQTT payload in this checkout, so the
native-size comparison is not a measured before/after MQTT bandwidth claim.
The revised encoder API view is 64 bytes because it now includes capture time.

Host ABI sizes reported by the tests (motion DTO 8, encoder DTO 16, frame
view 24 bytes) are transient host layouts and must not replace these wire
sizes or ARM measurements.

## Performance and remaining acceptance work

The optimized native GCC test measured about **9 ns per encoder encode/decode
pair** for one million iterations on this host. This microbenchmark excludes
RTOS access, encoder interrupts, sensors, copying to the network queue and
MQTT. It is not a target latency measurement or proof of a faster control loop.

Before claiming integrated hardware readiness:

- Buddy 1: implement length-aware copied binary handoff, test queue-full and
  disconnect behavior, then verify packets on the actual single MQTT topic.
- Buddies 2/4: verify wheel signs, ticks per distance, freshness limits and
  IMU/count alignment; test capture/clock rollover and reset of history.
- Controller/Buddy 2: measure renewal and expiry-to-PWM-off timing under
  concurrent MQTT/IMU/sonar/IR load, including rejected STOP requests.
- All owners: measure real task timing and stack high-water usage; rerun
  integrated static/dynamic RAM comparison after their payloads are adopted.
- Buddies 3/4/5: define their actual record schemas and regression evidence.

No recorded Zoom decision, hardware calibration, timing limit or test pass
has been invented to close these remaining items.
